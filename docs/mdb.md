# MDB 解码

本文解释“设备数据库里的一行，怎样变成程序里的一次检查”。安装和日常操作见
[README](../README.md)，补测后的处理见 [运维手册](operations.md#冷却期与补测v131-起)。

MDB 里存的是测量输入，不是本项目最终生成的报告：

| MDB 字段 | 白话含义 | 后续用途 |
|---|---|---|
| `al_r/al_l` | 右/左眼眼轴长度 AL，mm | 四公式计算；OAM |
| `r1_r/r1_l`、`r2_r/r2_l` | 两条角膜主子午线的曲率半径 r，mm | 换算 K；四公式计算；KER |
| `acd_r/acd_l` | 前房深度 ACD，mm | Haigis；OAM 段测量 |
| `axis_r/axis_l` | r1 对应子午线的散光轴位，度 | 报告与 KER；另一条轴位为 +90° |
| `state_r/state_l` | 操作员填写的眼部状态原文 | 报告与 OAM |

例如半径 `r = 7.80 mm` 按本项目口径换算为 `K = 337.5 / 7.80 ≈ 43.27 D`。
这是单位与字段示例，不是患者数据，也不用于临床校验。

## 数据源

设备活库 `IolmXP.MDB`（Jet 4 / Microsoft Access 2000 格式），
用 `access_parser` 纯 Python 读取，不依赖 JRE 或 ODBC。

表：`IolmMeasurements`，一次测量一行。

## 字段清单

| 字段 | 含义 | 缺失值处理 |
|---|---|---|
| `family_name` / `given_name` | 姓 / 名 | 用于姓名与记录归组 |
| `birth_date` / `exam_date` | 生日 / 就诊（业务）日期，可被改写 | 缺生日时不能生成 PatientID，显式报错 |
| `al_r` / `al_l` | 眼轴 mm | 缺 AL 的眼不生成 OAM |
| `r1_r` `r1_l` / `r2_r` `r2_l` | 角膜曲率半径 mm（不是 K） | 缺成对半径的眼不生成 KER |
| `acd_r` / `acd_l` | 前房深度 mm | 缺 ACD 时省略对应测量段 |
| `axis_r` / `axis_l` | 角膜散光轴位（K1 的轴） | 缺失时留空 |
| `state_r` / `state_l` | 晶状体 / 玻璃体状态，中文自由文本 | 保留原文；未填写时不猜测 |
| `patient_sex` | 性别 → DICOM PatientSex | 缺失或无法识别时留空 |
| `lens_thickness_*` | 晶状体厚度 | 本项目不使用 |
| `used_r` / `used_l` | 设备辅助字段 | 本项目不使用 |
| `guid` | 记录 ID | 与检查日期组成行级幂等键 |

不同检查可只包含部分测量值。缺 ACD 或其他字段不等于读取错误，
应按该字段实际可用性生成内容，不填 0 代替未测量。

### `exam_date` 是业务检查日期，与「测量是什么时候做的」是两件事

两个日期都在库里，含义不同：

| 字段 | 回答的问题 | 会不会被改 |
|---|---|---|
| `guid` 第 11 段（`YYMMDDHHMMSSmmm`） | 这批数据**是哪次采集**的 | 不会。改挂日期时 guid 不变 |
| `exam_date` | 这次检查**挂在哪一天的业务日期**下 | 会。同一 guid 可对应多个 `exam_date` |

同一原始采集记录可能被改挂到其他业务日期，二者不能混用。

所以 `exam_date` **既不是「测量时刻」，也不完全是「手填」**：它更像一个可被刷新、
可被改挂的**业务检查日期**。设备在「把一次测量归到某次就诊」时会改写它并新增一行，
数据也重新分析（见[分组逻辑](#分组逻辑)）。

由此有三条必须记住：

1. **判断「这批数据有多旧」只能看 guid**，不能看 `exam_date`。
2. **判断「哪一行属于这次就诊」看 `guid 日期 == exam_date`**，这是 `pick_row()`
   的第一判据。
3. **不要改分组键** —— `(姓, 名, exam_date)` 的语义是「这个人这次就诊」，本身是对的；
   升级不得随意更换幂等键，否则已有完成记录可能失效并触发重复发送。

「`exam_date` 当天新建但没测出值」**不等于**「这次检查没有数据」，也**不等于**
「可以拿几个月前那行顶上」—— 前者要按 `OTHER` 处理，后者要按 `STALE` 拦下。
`patient_sex` 字段可能为空。本项目读取并传递该值，DICOM 中的
`PatientSex` 在没有可用值时留空，不猜测性别。

性别归一化在 `core.patient.norm_sex()`：`M/m/Male/男/1` → `M`，
`F/female/女/2` → `F`，`O/Other/未知/unknown` → `O`；其他认不出的值
返回空串。空值保持为空，不猜性别。
本项目不使用 `lens_thickness` 参与计算。

## 关键换算

### K = 337.5 / r

`.iol` 和 MDB 都只存**角膜曲率半径 r (mm)**，不存 K (D)。

```
K(D) = 337.5 / r(mm)
```

这个 337.5 是角膜折射率 1.3375 的百分之一，也是 IOLMaster 打印机的换算基准。
字段换算应使用设备记录的半径与项目约定的换算常数逐项核对；文档不保留真实报告单数值。

> ⚠️ 历史 bug：曾写成 `0.3375 / r`，差 1000 倍，度数全错且不报错。
> 回归测试应同时核对单位和数值，不能只检查是否成功生成报告。

### 0 不是 NULL

**MDB 里未测出的字段存的是 0，不是 NULL。** 直接采信会让公式算出荒唐结果 ——
AL=0 时 SRK/T 会吐出几百 D。

`core/utils.num()` 把 `0` 和 `"0.0"` 一律当无效值：

```python
def num(v):
    s = str(v).strip()
    if s in ("", "0", "0.0", "0.00", "None", "NULL", "-"):
        return None
    ...
    return None if f == 0.0 else f
```

## 分组逻辑

`load_measurements()` 仍按 `(姓, 名, 检查日期)` 归组返回（这是取数层的接口），
但**管线不再在组内选一行**：v1.3.3 起**一行 = 一个案例**，幂等键是
`guid|exam_date`。同一天测两轮就是两个案例，各自判定、各自出单。

`pick_row()` 仍保留，用途只剩两处：迁移时判断「PACS 里那份内容来自哪一行」，
以及 `audit` 的多行明细展示。

### 组内多行到底是什么

同一 guid 可能出现在多个检查日期下：设备把同次采集改挂到另一个
业务日期后可新增一行，并重新分析测量值。以下仅为合成结构示例：

```
guid=synthetic-capture-a
  exam_date=20000102  测量版本 A
  exam_date=20000202  测量版本 B
```

所以同组多行既可能是「同一批数据改挂日期」，也可能是「当天新建但没测」。
**两种都不该按「谁后建」来选。**

### 选行口径：先看是不是当天，再看有没有值

`pick_row()` 的第一判据是 **`guid 日期 == exam_date`**（下称「当天」），不是
「有没有测量值」：

| pick | 含义 | 管线怎么做 |
|---|---|---|
| `OWN` | 当天采集，且这行有测量值 | 直接出单 |
| `OTHER` | 当天有记录，但没测出值 | 判「本次就诊尚无数据」，不出单（不拿别日期的顶上） |
| `STALE` | 组内没有当天的行，只有别日期的数据 | v1.3.3 起**不再拦单**（见下） |
| `EMPTY` | 整组没有任何可录入的测量值 | 跳过 |
| `PUSHED` | **仅限已推记录**：PACS 里那份内容的来源行 | 只比对 / 补写指纹，永不推送 |

**为什么不能「有测量值优先」**：当天行为空、旧行有值时，按有值优先
会将历史测量按今天的业务日期出单，造成数据时效性的误解。

**为什么也不能只看日期**：当天行有值时按正常路径处理；当天行为空时，
必须明确区分本次无数据与其他日期的历史数据，不能用旧值填补空行。
这些选行结论供兼容接口和审计使用；v1.3.3 起管线逐行处理，不再组内选单。

### 已推过的记录问的是另一个问题

同一个 key，已推过和没推过要选的行**可能不同**：

| 场景 | 该问的问题 | 调用 | 可能返回 |
|---|---|---|---|
| 从没推过 | 「这次就诊该用哪一行出单？」 | `pick_row(rows)` | `OWN` / `OTHER` / `STALE` / `EMPTY` |
| 已推过（`done` 里有） | 「PACS 里那份内容是哪一行推出去的？」 | `pick_row(rows, already_pushed=True)` | `PUSHED` / `EMPTY` |

`PUSHED` 是独立取值，不复用 `OWN` / `STALE`：来源行可以早于业务
日期，这不否定它是旧版已推内容的来源。空行不能生成实例，按出单口径
选择当天空行可能误判已推记录为无有效测量。将两种判断分开，避免调用方
遗漏已推状态判断而错误地阻断记录。

`already_pushed=True` 只用于**比对指纹 / 补写指纹 / 判陈旧**，这条路径永远
不会触发推送。

> `pick_latest()`（只按 guid 时刻）与 `pick_best()`（只要行、不要结论）
> **保留原样不删**：兼容可能依赖这些函数的外部脚本。
> 管线内部一律用 `pick_row()` —— 丢掉了 pick 结论就没法判断该不该推。

### 现场怎么自查

```bash
# 只读，不改 state、不推 PACS
/opt/iol2dcm/venv/bin/python /opt/iol2dcm/pipeline.py audit
```

审计的「同日同名多行」部分用于解释选行依据：`*` 标记选中行，
「当天」表示 guid 的采集日期等于 `exam_date`，否则显示采集日期。
以下为合成输出：

```
· 同日同名多行（选行依据，仅供参考）  1 条
    · 行0 空/当天/20000102  *行1 有值/19991201/20000102
```

当天行为空、历史行有值时，应检查测量来源与业务日期。v1.3.3 起管线逐行处理，
审计中的选行说明不再作为跨日期拦单条件。普通已推记录的补测由 Rec N 路径
自动处理；身份冲突或空测量等安全暂停原因见运维手册。

而**同日同名两行生日不同**不算需要处理的情况：按使用者口径，那是两条独立
记录，当两个人看，管线不做核对、不建待办。它只出现在上面「同日同名多行」
的只读清单里（两行生日都会印出来），不计入结论。

自检行（姓名以 `!` 开头，或含 `CHECK`）跳过 —— 那是设备开机自检写进去的，
不包含真实测量。

## 为什么不用 `.iol` 文件

设备每次检查还会导出一个 `.iol`，但有两个硬伤：

1. **`.iol` 里完全没有散光轴位**，轴位只能从 MDB 补。
2. **`.iol` 的公式表是厂商算的**，本项目要自己的四公式，还得重新算一遍。

而 MDB 一次检查一行、含轴位、天然可按日期筛选。以 MDB 为唯一数据源更干净。

## 落盘判定：mtime 变了不等于写完了

`watch` 靠 mtime 判断有没有新检查，但**设备写 Access 库时 mtime 先变、
页还在刷**。此时去 `access_parser` 解析，最坏情况会读出半写入的浮点字节，
然后按错误度数出单推给 PACS —— 而且不会报任何错。

所以读之前先等文件「指纹」稳定（`sources/mdb.wait_settled`）：

```
指纹 = (st_mtime_ns, st_size)
连续 settle_seconds 秒指纹不变  ->  认为写完，可以读
超过 settle_timeout_seconds 还在变  ->  本轮跳过，下轮再看
```

用 `st_mtime_ns` 而不是 `st_mtime`：秒级精度下同一秒内的两次写入指纹相同，
会被误判成"已稳定"。size 一起比是因为原地改写页时某些挂载的 mtime 精度粗，
但页数变化会体现在 size 上。

配置在 `config.yaml` 的 `watcher.settle_seconds`（默认 5）与
`watcher.settle_timeout_seconds`（默认 120）。代价是每次 MDB 更新后
出单延迟多 5 秒。

**为什么不用 `.ldb` 锁文件**：设备机器开着，`.ldb` 就一直存在。它标记的是
"库被 Access 引擎打开"，不是"正在写"，无法区分空闲与写入。

稳定检测行为（`sources/mdb.wait_settled`）：

| 场景 | 结果 |
|---|---|
| 文件静止 | settle 秒后判定稳定 |
| 持续写入 | 超时返回 False，本轮跳过并打日志 |
| 写入停止后 | settle 秒后判定稳定，恢复处理 |
| 文件不存在 | 立即返回 (False, None) |
| 同秒内两次写入 | mtime_ns 能区分 |
| size 不变但内容变 | mtime_ns 能区分 |

读库失败（`load_measurements` 抛异常）现在显式返回空统计并打日志，
不再冒泡到 `loop()` 的 `except` —— 否则只会打一行 traceback，
看不出"这一轮白跑了"。

## 结构校验

启动时 `mdb.assert_supported()` 检查 10 个必需字段。

| 层 | 字段 |
|---|---|
| 必需（缺一即停） | `family_name given_name birth_date exam_date al_r al_l r1_r r1_l r2_r r2_l` |
| 可选（缺则跳过对应内容） | `acd_r acd_l`（缺 → Haigis 不出）<br>`axis_r axis_l`（缺 → 报告单无轴位）<br>`patient_sex`（缺或空 → PatientSex 留空）<br>`guid` |

**为什么必须校验**：IOLMaster 700 用的是 `CZM_*.MDB` 系列（表名 `GeneralStudy_M` 这类
DICOM 风格），结构完全不同。指错了库时 `access_parser` 要么抛
`'NoneType' object has no attribute 'parse'`、要么读出全 None，然后公式算出
荒唐的度数 —— **而且不会报任何错**。

结构不兼容时的错误输出示例：

```
✗ 库结构与本项目验证过的 IOLMaster 500 结构不符，已停止。
  库文件   : /path/CZM_latest.MDB
  表       : IolmMeasurements
  原因     : 表 IolmMeasurements 不存在
  存在的表 : ClinicalTrialSeries_M, GeneralStudy_M, GeneralSeries_M, ...
  缺少字段 : family_name, given_name, birth_date, exam_date, al_r, al_l, ...
```

## 眼状态字段的坑

`state_r` / `state_l` 是操作员录入的中文自由文本，
可出现不同术语和组合，例如：

```
有晶状体 / None / 硅油充填眼 / 硅油充填眼，有晶状体 / 无晶状体
硅油填充眼，无晶状体 / Phakic / 无晶状体硅油填充眼
人工晶状体PMMA / 假晶状体硅油充填眼 / 硅油充填眼，人工晶状体
人工晶状体丙烯酸酯
```

连「充填」和「填充」、「人工晶体」和「人工晶状体」都混用。

**处理方式：原文直封进 DICOM，不做翻译。** 映射必然要猜（「硅油充填眼」
没说晶状体状态，「人工晶体」少个「状」字），猜错比不猜更糟。详见
[dicom.md](dicom.md#眼状态原文直封不做翻译)。

报告单上的「眼状态」行同样印原文；设备未填时印 `None`
（不是「测不出」—— `测不出` 是留给 AL/K/ACD 这类仪器测不出来的场景）。

## 数据质量备忘

| 问题 | 影响 | 处理 |
|---|---|---|
| 空检查（没有有效测量） | 出单通篇「测不出」无临床价值 | 判据：双眼全无 AL，且没有成对的 r1+r2 → 不生成实例；仅有 ACD 或眼状态也不算有效测量 |
| 姓名可能被录成拼音 | DICOM PN 拼装规则不同 | `is_cjk()` 判断字符而非字段位置 |
| 同一患者同日多次检查 | 会重复出单 | v1.3.3 起**有意如此**：一行 = 一个案例，同天两轮各出一个 study |
| 同一 guid 挂在多个日期下 | 每行各自成案例 | v1.3.3：一行一个案例，按各自数据走「信息是否充足」判定；`audit` 里只读提示 |
| 同日同名两行生日不同 | 是两条独立记录，不是数据错误 | 当两个人处理：不做核对、不进待办；`audit` 的「同日同名多行」会列出两行生日 |
| 生日常见 1909-09-09 这类占位值 | PatientID 撞车 | 无解，只能靠姓名摘要区分 |
